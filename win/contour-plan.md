# Контур тестирования на Windows-машине (Фаза 3) — чертёж для обкатки

Дата: 2026-10-01. Статус: скрипты-заготовки; константы (версия платформы,
пути, имя бэкапа) заполняются при первом прогоне на Pers-Pool03.

## Целевой конвейер (по роадмапу, Фаза 3)

```
снапшот/чистое состояние → ночной бэкап (.dt) → ibcmd restore
→ import XML из git-ветки → ibcmd check → YAxUnit-дым → пруфы в MR
```

## Скрипты

- `contour-restore.ps1` — восстановление тестовой базы из .dt через ibcmd.
- `contour-import.ps1` — загрузка XML-дерева конфигурации из рабочего клона.
- `contour-check.ps1` — прогон /CheckConfig и сбор лога (fail-closed).

Общий принцип (из docs/05, контракт надёжности): код возврата любого шага ≠ 0
→ цепочка останавливается, артефакты сохраняются, MR не публикуется.

## Что нужно замерить на машине (первый прогон руками/через агента)

1. Путь к платформе: `C:\Program Files\1cv8\<версия>\bin\ibcmd.exe`
   (Community-версия 8.3.23+ — проверить установленную).
2. Каталог бэкапов: где появляются ночные .dt (сетевой шарой или локально).
3. Сервер СУБД тестовой базы: файловая ИБ или PostgreSQL (имя/порт/учётка).
4. Права: может ли учётка машины писать в каталог баз и читать бэкапы.
5. Ресурсы: RAM/CPU (для лимитов параллельных прогонов).
6. Доступность litellm-dev.utmn.ru и gitlab/jira изнутри машины (ping/curl).

## Команды ibcmd (каркас; флаги уточнить по версии платформы)

```bat
:: восстановление из .dt в файловую базу
ibcmd infobase restore --db-path=C:\1c-vibe\ib --restore-file=C:\backups\night.dt

:: применение выгрузки (XML) из git-клона
ibcmd infobase config import --db-path=C:\1c-vibe\ib --config-files=C:\1c-vibe\repo\dump

:: проверка конфигурации
ibcmd infobase config check --db-path=C:\1c-vibe\ib --check-logical=true > check.log
```

Параметры `--db-path`/`--restore-file` и состав команд зависят от версии
ibcmd — сверить с `ibcmd infobase --help` на машине; расхождения занести
сюда и вskills.

## Критерий готовности Фазы 3

По MR агента автоматически поднимается база из бэкапа, применяется ветка,
прогоняется проверка; лог и отчёт прикладываются к MR как пруфы.
