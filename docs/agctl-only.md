## Решение

Единственный целевой путь запуска 1c-vibe — **через agctl**.
Пользователь получает готовый бинарь agctl, бинарь создаёт рабочее место
1c-vibe (bare-origin + рабочий клон + изолированный DSH_HOME + Docker-контейнер
с dsh web), человек работает с агентом в dsh web. Отдельных поддерживаемых
режимов «вне agctl» нет.

Переходная форма — **CLI-first того же agctl**: бинарь создаёт/запускает
рабочее место из командной строки и печатает ссылку на dsh web, без
развёрнутой веб-панели ЛК agctl. Панель ЛК (многопользовательский сервер
с авторизацией и HTTPS) — следующий этап. «agctl без панели» — это всё
ещё режим через agctl, а не standalone: provisioning, DSH_HOME и контейнер
делает тот же код agctl, руками ничего собирать не нужно.

Что это значит на практике:

- Новую функциональность проектируем только под agctl-путь.
- Баги standalone-путей не чиним, доки по ним не развиваем.
- Код standalone-путей пока **не удаляем** (лежит на месте до отдельного
  аудита удаления) — но он legacy, см. карту ниже.

## Legacy-карта: что относится к B1–B3, а что — нет

Легенда: `LEGACY` — не поддерживается, не развивать, удалить только
отдельным аудитом; `ACTIVE` — целевой путь / переиспользуется в agctl.

### LEGACY — B1: dsh web на хосте

| Путь | Что это |
|---|---|
| `docs/onboarding.md` (§§1–7) | Ручная установка dsh на хост, ручной провайдер, ручной скилл |
| `scripts/cleanroom-dsh.sh` | Отдельный DSH_HOME + `dsh web` на хосте (инструмент B1) |

### LEGACY — B2: изолированный dsh-home в репе

| Путь | Что это |
|---|---|
| `dsh-home/` (всё, кроме `cordis.patch.yml`) | Живые сессии, settings, profiles локального B2-запуска; в git не трекается (см. `.gitignore`), на agctl-путь не влияет |
| `AGENTS.md` (процедура «изолированного dsh-агента») | B2-процедура; действует переходно, пока нет agctl CLI, затем заменяется agctl-онбордингом |

Исключение: `dsh-home/cordis.patch.yml` — трёхстрочный плейсхолдер
(пустой патч), оставлен как подсказка для шаблона agctl. ACTIVE как
заготовка, не как рантайм.

### LEGACY — B3: harness-free петля `agent/`

| Путь | Что это |
|---|---|
| `agent/loop.py`, `agent/llm.py`, `agent/tools.py`, `agent/guard.py`, `agent/llmcheck.py` | Самописная Python-петля (не DSH); исполнитель B3 |
| `agent/test_agent.py`, `agent/test_loop_offline.py` | Тесты B3-петли |
| `win/bootstrap.ps1` | Подготовка машины + вызов `agent/llmcheck.py` (точка входа B3) |
| `win/make_bundle.py`, `win/receive_bundle.py` | Base64-бандл кода для доставки B3 на машину контура |
| `mvp/main.py` | Заглушка `print("Hello from mvp!")` (uv-стартер), нигде не используется |

### Секреты в agctl-пути (фиксация против дрейфа)

Токен LLM хранится в ЛК agctl шифротекстом (AES-256-GCM, мастер-ключ
в `AGCTL_HOME/secrets.key`), в контейнер приезжает через env
`AGCTL_LLM_API_KEY`. Отдельно: текущий код agctl также пишет открытый
токен в `dsh-home/.credentials.yaml` — это известная недоделка, перед
боевым использованием убрать или обосновать (не часть данного решения).
