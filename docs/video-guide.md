# Видео-гайд: сквозной прогон 1c-vibe через agctl (что кликать по порядку)

Статус: **черновик**. Подтвердить шагами D–E (`clean-machine-run`, `live-jira-mr`),
потом снимать. Цель видео: новый человек смотрит и становится прошаренным
пользователем — понимает, что кликать и что происходит под капотом.

Ориентир по хронометражу: ~15 минут (0–10 workflow, 10–13 «под капотом», 13–15 «что дальше»).

## 0. Подготовка (за кадром, показать списком на 20 секунд)

- Чистая машина: Go, Docker (Desktop/dockerd запущен), git.
- Доступы: VPN в сеть UTMN; токены Jira и GitLab (scope `api`); ключ LiteLLM.
- Что сказать: «Нам нужен только agctl — dsh, Node и изоляция уже внутри его образа, на хосте их ставить не надо».

## 1. Запуск agctl (терминал, ~1 мин)

```
cd agctl
make demo
```

- Показать лог сборки и строку `serve: addr=...`.
- Открыть напечатанный адрес в браузере (по умолчанию `http://127.0.0.1:8929`).
- Что сказать: «Один бинарь — и ЛК, и provision, и Docker».

## 2. Регистрация + создание рабочего места (~2 мин)

1. Зарегистрироваться (первый пользователь = админ).
2. «Создать рабочее место», имя любое, шаблон **1c-vibe**.
3. Ввести Base URL `https://litellm-dev.utmn.ru/v1`, модели `qwen-3.8-deep`
   (+ `qwen-3.8-fast`), токен LiteLLM.
4. Показать статус `provisioning → running` («колесико»).
5. Что сказать: «Платформа сейчас создаёт bare-репу, рабочий клон и контейнер».

## 3. Открыть dsh web (~30 сек)

- Кнопка «Открыть» у рабочего места → dsh web воркспейса.
- Что сказать: «Это интерфейс агента. Ссылка с одноразовым токеном — голый URL без него даст 401».

## 4. Настроить контур внутри (терминал dsh web, ~2 мин)

```
cd scripts
cp .env.example .env
# вписать JIRA_URL/JIRA_TOKEN, GITLAB_URL/GITLAB_TOKEN
python3 -m pytest tests/ -q
```

- Показать зелёные тесты.
- Что сказать: «Тулзы контура едут вместе с рабочим местом; токены только в `.env`, он в git не попадает».

## 5. Задача агенту (~4 мин, сердце видео)

- Написать агенту: «выполни INTAIDEV-N по скиллу 1c-vibe-demo».
- Ускоренно показать: чтение задачи → ветка `agent/INTAIDEV-N` → правка XML/BSL → линтер → публикация.
- Что сказать: «Я только смотрю. Агент сам готовит ветку, правит, проверяется и публикует».

## 6. Пруфы: MR + Jira (~1 мин)

- Открыть Merge Request в GitLab: дифф + CI.
- Открыть задачу в Jira: комментарий агента со ссылкой на MR.
- Что сказать: «Человек контролирует и вмерживает. MR — единственный путь публикации».

## 7. Живучесть: stop/start (~1 мин)

- В ЛК остановить и снова запустить рабочее место, показать что файлы и сессии на месте.
- Что сказать: «Контейнер расходный: работа живёт в git-клоне (autosave каждые 2 минуты) и DSH_HOME на диске».

## 8. Под капотом за 3 минуты (схема на словах)

1. Два git-хранилища: bare-origin («эмуляция GitLab») + рабочий клон.
2. В контейнер смонтированы ровно две вещи: клон (`/workspace`) и DSH_HOME (`/home/dsh`) — поэтому контейнер можно пересоздавать.
3. Секреты: в ЛК шифруются (AES-GCM), в контейнер едут через env.
4. Windows-VM с 1С — отдельно: платформа 1С не живёт в Linux-контейнере, это внешний инструмент воркспейса, не часть этого видео.

## 9. Финал (~30 сек)

- Что дальше: Windows-контур (тестовая база, скриншотная петля), Jira-триггер фонового агента, CLI-команда создания места.
- Призыв: «Заведите рабочее место и возьмите первую INTAIDEV-задачу».

## Заметки для монтажа

- Токены и `?token=` в URL блюрить.
- `docker logs` целиком не показывать (там бывает boot-токен).
- Если provision упал — смотреть логи места в ЛК, чинить, не переснимать всё с нуля.
