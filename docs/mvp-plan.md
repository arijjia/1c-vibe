# MVP 1c-vibe: агент «Jira → код → Merge Request → комментарий в Jira»

Дата: 02.09.2026. Это план первого работающего MVP — того самого демо, которое просил руководитель (пункты 3–4): агент читает задачу в Jira, делает правки в демо-репозитории GitLab, открывает Merge Request и оставляет комментарий под задачей со ссылкой на MR.

## 1. Что MVP доказывает и чего в нём нет

**Доказывает:** замкнутый цикл «задача → ветка → правка → MR с проверкой → отчёт в задаче» без единого ручного клика; подход «скиллы + CLI» (агент работает через инструкции и скрипты, без MCP-обвязки); воспроизводимость (одна и та же процедура на любой задаче).

**Специально нет (осознанный скоуп):** платформы 1С, тестового контура, реальных данных, хранилища 1С. Демо-репозиторий — синтетическое 1С-дерево (XML + BSL). Проверка правок — статический анализ BSL Language Server (headless, платформа не нужна). Всё «1С-ное» подключится позже поверх того же каркаса — это прямая задача Фазы 2–3 основного роадмапа.

**Почему это не «вслепую»:** линтер даёт агенту обратную связь (синтаксис, стандарты 1С), а CI в GitLab делает её видимой для человека в MR. Полноценные тесты (YAxUnit/Vanessa) требуют контура — в демо это честно показываем как следующий шаг.

## 2. Архитектура

```
┌──────────────┐   1. взять задачу    ┌──────────────────────────────┐
│ Jira         │ ───────────────────► │ Агент (ноутбук Маши)          │
│ INTAIDEV-xxx │ ◄─────────────────── │ opencode / DeepSeek Harness   │
└──────────────┘   6. комментарий     │ + скилл «1c-vibe-demo»        │
                  со ссылкой на MR    │ + модель (любой endpoint)      │
                                      └───────┬──────────────────────┘
                                              │ 2. клонировать demo-репо
                                              │ 3. найти объект, править XML/BSL
                                              ▼
                                   ┌──────────────────────────────┐
                                   │ GitLab: 1c-vibe-demo          │
                                   │ ветка agent/INTAIDEV-xxx      │
                                   │ 4. commit + push              │
                                   │ 5. Merge Request              │
                                   │ CI: BSL LS (статика)          │
                                   └──────────────────────────────┘
```

Компоненты:

| Компонент | Что это | Файлы |
|---|---|---|
| Демо-репозиторий | Синтетическое дерево 1С (справочник «Товары» + модули) + CI с линтером | `mvp/demo-project/` |
| Интеграция Jira | REST-клиент: прочитать задачу, добавить комментарий | `mvp/jira_client.py` |
| Интеграция GitLab | REST-клиент: проект, создать MR | `mvp/gitlab_client.py` |
| Публикация | Ветка → commit → push → MR → комментарий в Jira | `mvp/publish.py` |
| Скилл агента | Пошаговая инструкция для харнеса | `mvp/skills/1c-vibe-demo/SKILL.md` |
| Конфиг | Адреса и токены через `.env` (не в git) | `mvp/.env.example` |

Принципы: чистый Python без зависимостей (stdlib); токены только в `.env`; агент вызывает скрипты как обычные CLI-команды (никаких MCP ради MVP); каждый шаг логируется.

## 3. Поток выполнения (демо-сценарий)

1. В Jira создана задача, например «INTAIDEV-101: В функции Приветствие добавить проверку пустого наименования» (тексты трёх демо-задач — в `demo-project/tasks/demo-tasks.md`).
2. Маша запускает агента: «выполни задачу INTAIDEV-101 по скиллу 1c-vibe-demo».
3. Агент: `python mvp/jira_client.py get INTAIDEV-101` → читает постановку.
4. Агент клонирует demo-репо и до правок запускает
   `publish.py INTAIDEV-101 --repo <клон> --prepare`:
   скрипт обновляет refs и создаёт чистую ветку `agent/INTAIDEV-101` от основной.
5. Агент находит нужные файлы, вносит минимальную правку и проверяет себя:
   локальный BSL LS + чтение diff.
6. Агент: `python mvp/publish.py INTAIDEV-101 "резюме" --repo <клон>` →
   коммит, безопасный push, MR с описанием.
7. Агент добавляет комментарий в Jira: что сделано, ссылка на MR, как проверял.
8. Маша открывает MR: дифф + CI. Смерживает (или просит переделать — агент повторяет).

Критерий успеха MVP: **три демо-задачи подряд проходят путь 1–8 без ручных правок кода человеком**.

## 4. Роадмап

### M0. Доступы и площадки (зависит от Маши)
- [ ] GitLab: создать пустой проект `1c-vibe-demo` (в группе для тестов), выдать PAT (scope `api`).
- [ ] GitLab Runner: Docker executor, доступ к Docker Hub и GitHub Releases; либо внутреннее зеркало образа и jar.
- [ ] Jira: уточнить Server/DC или Cloud; дать тестовый project key и право читать задачи/писать комментарии. Для Server/DC — PAT, для Cloud — email+API token.
- [ ] Модель: решить, какой endpoint использует агент (уже настроенный opencode / DeepSeek API / локальная Ollama — в демо нет ПДн, подходит любой).
- **Готовность:** `.env` заполнен, `python mvp/jira_client.py get <демо-задача>` и `gitlab_client.py whoami` отвечают без ошибок.

### M1. Демо-репозиторий
- [x] Локально создано синтетическое дерево XML + BSL, три постановки и CI-конфиг.
- [x] BSL LS 1.0.7 проверен локально; версия и SHA-256 закреплены; отчёт читается fail-closed.
- [ ] Запушить содержимое `mvp/demo-project/` в новый проект.
- [ ] Подтвердить зелёный job на реальном GitLab Runner.
- **Готовность:** MR с намеренной ошибкой в .bsl красит CI; без ошибки — зелёный.

### M2. Интеграции вручную

## 5. Риски и запасные варианты

| Риск | План B |
|---|---|
| У GitLab-проекта нет раннеров / раннер без интернета | Линт локально у агента (Java на маке), CI добавим позже |
| Jira окажется Cloud, а не Server | Другая схема авторизации в jira_client.py (email+token basic) — 10 строк |
| Модель слабая для правок BSL | Демо-задачи простые; скилл содержит готовые паттерны; при необходимости меняем endpoint |
| Токены утекут в git | Токены только в `mvp/.env` (в .gitignore); в коде нет адресов/секретов |
| Подменённый `origin` украдёт GitLab-токен | Перед HTTPS push хост origin обязан совпасть с `GITLAB_URL`; токен передаётся через временный askpass |
| Линтер не запустился, но CI зелёный | Fail-closed: без корректного `bsl-json.json` job падает; jar закреплён версией и SHA-256 |

## 6. Что дальше после MVP (мостики к основному плану)

- Демо-дерево → реальное дерево `1c-university`: тот же скилл, шаги не меняются (это проверка тезиса «агенту достаточно git»).

- Комментарий в Jira → полный пакет пруфов (отчёты тестов, скриншоты из контура).
- Мост в хранилище (О3) надстраивается над тем же publish-механизмом.
